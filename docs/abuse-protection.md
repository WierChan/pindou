# 防刷与成本防线（pindou-server 实现）

设计目标只有一句话：**刷子碰得到的每一道门都按微信身份限额，额度定在真人永远碰不到的高度**。
不上验证码、不上滑块、不加任何打扰普通用户的东西——小程序生态里每个请求天然绑定
真实微信号（openid），刷子必须消耗真实微信账号，这本身就是最贵的门槛，用好它就够了。

## 0. 先认清攻击面：哪些接口真的花钱

客户端的重活（图片转图纸、图纸识别、渲染、导出）**全部在用户手机上跑，不消耗服务器**。
真正打到服务器的只有下面这些，成本从高到低：

| 接口 | 成本构成 | 风险 |
|---|---|---|
| PUT /api/works/:id（作品同步上行） | 存储 + 带宽（整包 payload，大作品数百 KB） | **最大头**：写入放大、存储膨胀 |
| POST /api/patterns（生成导入码） | 存储 + **msgSecCheck 调用**（有每日配额，刷爆了功能瘫痪） | 配额耗尽 → 全体用户不能生成口令 |
| GET /api/works /api/works/:id（同步下行） | 带宽 | 拉取洪水 |
| GET /api/patterns/code/:code | 带宽 | 枚举扫描（码空间 31^8 扫不动，但流量要拦） |
| POST /api/auth/login | code2session（微信侧也有配额）+ DB | 登录洪水 |
| GET /api/config /api/templates | 极低，可缓存 | 忽略（加缓存头即可） |

客户端已配合的降载（本仓库已实现，服务端可以按此估算真人基线）：

- 拼豆进度推送防抖 1.5s → **20s 尾沿触发**（停手 20s 才推一次，边拼边传的持续上行没有了）
- 首页 syncAll 加 **60s 冷却**（前后台切换不再次次全量同步）
- token 持久化（正常用户几乎不重复 login）、templates 会话缓存、口令生成幂等（clientWorkId）

## 1. 主防线：按 openid 配额（核心，全部接口）

原则：**额度 = 真人重度用户的 10 倍以上**。真人永远撞不到墙；撞到墙的都不是真人。
超限统一返回 `{code: 429, message: "操作太频繁，稍后再试"}`——客户端已有对应降级
（同步失败进挂起队列自动重试、口令生成失败 toast），429 不会造成任何数据丢失。

建议额度（Redis 滑窗或计数器，按 openid）：

| 接口 | 限额 | 依据 |
|---|---|---|
| PUT /api/works/:id | 60 次/小时、600 次/日 | 防抖 20s 下重度玩家 ≈ 每小时 20-30 次 |
| GET /api/works | 30 次/小时 | 冷却 60s 下正常 ≈ 每小时几次 |
| GET /api/works/:id | 300 次/小时 | 新设备首次全量拉取需要余量 |
| DELETE /api/works/:id | 100 次/日 | |
| POST /api/patterns | 20 次/日（已在导入码文档建议） | 正常人一天分享不了几幅 |
| GET /api/patterns/code/:code | 60 次/小时（已建议）；另见 §3 枚举拦截 | |
| POST …/report | 10 次/日 | |
| POST /api/auth/login | 每 IP 60 次/小时（login 时还没有 openid） | 正常用户 token 长期有效，几乎不 login |

存量硬上限（配额之外的绝对墙，防慢刷囤积）：

- 单用户云端作品数 ≤ **300**；单作品 payload ≤ **600KB**（w、h ≤ 256 服务端校验，超限 400 拒收）
- 单用户导入码档案数 ≤ **200**

## 2. 保底熔断：保护钱包和微信配额

按 openid 的配额挡单个刷子；**全局熔断**挡账号矩阵（一百个小号各刷额度内的量）：

- **msgSecCheck 全局日熔断**：当日调用达到微信配额的 80% → 生成导入码接口整体降级，
  返回「今日分享名额已满，明天再来」。宁可功能停一晚，不能配额耗尽连累其他校验场景
- 每接口全局 QPS 基线告警：超过 7 日均值 5 倍 → 告警到你的微信/邮箱（不自动封，先看）
- 存储总量周报：DB 尺寸、top 20 openid 的存储/请求排行——刷子在排行榜上一眼可见

## 3. 异常模式识别（轻量即可，不搞风控系统）

- **口令枚举**：单 openid 一小时内 `GET /api/patterns/code/:code` 命中 404 超过 20 次 →
  该 openid 此接口封 1 小时。码空间 8500 亿本来就扫不动，这条只是省流量
- **新号高频**：注册 < 24h 的 openid 触发任一 429 → 当日全接口额度减半。老实新用户根本
  碰不到 429，碰到的减半也够用
- **处置抓手**：openid 黑名单表（命中全接口 429），后台手动加/解封。配合导入码已有的
  status=disabled，两个抓手足够处理早期一切滥用

## 4. 部署侧顺手做的

- nginx/网关层 `limit_req` 按 IP 粗限（如 30r/s burst 60）：挡纯 IP 洪水，一行配置
- 校验 `Referer: https://servicewechat.com/{appid}/...`：只能挡最懒的脚本（可伪造），
  但也是一行配置，顺手加
- GET /api/config、/api/templates 加 `Cache-Control` / ETag；templates 变更频率低，
  甚至可以直接扔 CDN

## 5. 明确不做的（都会伤真人，且在微信生态里收益极低）

- ❌ 验证码 / 滑块 / 短信验证——微信身份已经比这些都硬
- ❌ 设备指纹 SDK——隐私审查风险 > 收益
- ❌ 按 IP 精细限频（NAT 下一栋楼共享出口 IP，会误伤一片真人；IP 只做网关层粗限）
- ❌ 注册冷静期 / 新号禁用功能——新用户第一天恰恰是最活跃的一天

## 上线顺序建议

1. **第一批（上线前必须有）**：§1 的 openid 配额 + payload/存量硬上限 + msgSecCheck 熔断
2. **第二批（有流量后）**：QPS 告警 + top 排行周报 + 黑名单后台
3. **观察调参**：所有额度上线后按真实 P99 复核，只放宽不收紧（收紧才需要谨慎）
